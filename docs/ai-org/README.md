# AI組織 設計書｜AI業務効率化支援事業部

作成: 2026-07-26 ／ 運用形態: Claude Code Routine（スケジュール実行）

事業部の案件取りまとめ（デリバリー進捗・継続率・アップセル/クロスセル・経営報告）を、
定例MTGと最終承認以外は人を介さずAIが遂行するための組織設計。

> **注意**: このリポジトリは公開のため、本設計書にはクライアント名・金額等の固有情報を含めない。
> 固有情報（案件・パイプライン・レポート）はすべてNotion社内ページ「AI組織 運行ボード」に置く。

| 事業責任者（人間） | 最小化が目標 | リアルMTG・新規商談クロージング・期待値調整/クレーム・送信の実行・金額/契約の最終判断 |

## MTG委任ポリシー

事業責任者の時間を経営に最大化するため、MTGは次の基準で仕分ける:

| 区分 | 出席者 | AIの支援 |
|---|---|---|
| オンライン進捗定例 | 担当スタッフ | 前日までに準備パック（アジェンダ・進捗・宿題・想定Q&A）を運行ボードに生成 |
| 型どおりのアップセル商談（既存顧客・標準枠） | 担当スタッフ | トーク骨子・提案ドラフトを準備パックに同梱。クロージング判断に迷えば持ち帰り |
| リアルMTG・新規商談クロージング・期待値調整/クレーム | 事業責任者 | 準備パック＋事前ブリーフ |

- MTG後はZoom議事録から決定事項を台帳へ反映（AI）
- スタッフへの割当はAIの「提案」であり、確定は人間が行う
- 毎週金曜の出番監査で、委任度（責任者出席MTG数/全MTG数）と拘束時間の推移を計測する

## 役務提供の分担（AIが実働する）

デリバリー（役務提供）はAIが実行主体。人間は AIが物理的に代替できない部分のみ担当する。

| 区分 | 担当 |
|---|---|
| コード・スクリプト・HTMLデモ/フォーム・設計図ドラフト・文書・データ整理・調査・回答ドラフト | **AI**（日次巡回内で実行、成果物はリポジトリ/運行ボードへ） |
| 認証・アカウント権限付与・本番デプロイ・実機/現地設定 | 人間（「人間ブロッカー」として担当者名付きで運行ログに分離明記） |
| クライアントへの送信（メール・チャット） | 人間（AIが完成状態の文面を用意し、送信ボタンのみ人間） |
| リアルMTG | 人間（AIが準備パック＋事前ブリーフを用意） |

- 即レス即納の原則: 問い合わせ・依頼の回答ドラフトは即日作成
- ただし期日・可否の約束は即答禁止ゲート（2営業日以内に3点セット）を維持

## 納期規律（機会損失の最小化）

完了要件・工数・納期が曖昧なまま走り出すと納期がずるずる後退し、
納品完了をトリガーとする次サイクル・追加提案まで凍結される（=機会損失）。
これを構造的に防ぐ3つの関所を設ける。

**1. 着手ゲート** — 次の3点が揃わない案件は構築を開始しない。
欠けていればAIが即日ドラフトを起票して充足させる:

- 受入基準（完了要件チェックリスト。「何ができたら納品か」）
- タスク分解と工数見積
- バッファ付きマイルストーン: **内部納期 = 見積×1.5 ／ 対外約束 = 内部納期＋5営業日**
  （早く納めて「前倒し納品」の感動を作る。ギリギリの約束はしない）

**2. スコープ変更の関所** — 新規要望・仕様変更は必ず「納期影響＋X日」の
影響見積を付け、「パーキングロット行き or 納期再設定」の二択で整理する。
黙ってスコープに吸収させない（仕様凍結後の手戻り防止）。

**3. 納期の正本管理** — 納期は案件DBのプロパティが唯一の正本。
口頭・チャットでの納期変更を検知したら、正本に反映するか差し戻すかをアラートし、
記録なき納期変更を残さない。

**機会損失の計測** — 遅延案件ごとに「遅延日数×原因分類（当社実装／先方ボール／
仕様変更／その他）」と「凍結中の金額（当該案件の想定月額＋納品完了トリガー待ちの
追加提案額）」を集計し、週次で金額表示する。着手ゲート3点の充足率も週次で追う。

## 顧客教育プロトコル（教育ラダー）

先方起因の停滞（ボール滞留3営業日超）・丸投げ・他責パターンには、関係を壊さず
プロジェクトを前に進めるための段階的な教育を適用する。トーンは常に
「プロジェクト成功のため」フレームで、顧客満足度を守る。

| 段階 | 施策 | 実行 |
|---|---|---|
| L1 | 期限＋未回答時デフォルト付きリマインド（「◯/◯までにご返答なき場合は△案で進めます」） | AIが文面作成→人間が送信 |
| L2 | 共有ページの宿題欄に双方の宿題・期限・滞留日数を事実として明記 | AI |
| L3 | 完了定義・役割分担の握り直しアジェンダを次回定例の準備パックに同梱 | AI作成→担当スタッフが定例で実施 |
| L4 | 期待値調整・スコープ再交渉（重症例のみ） | 事業責任者（AIが週報で要否判断を提示） |

各役割の詳細手順は `routines/` 配下:

- [`routines/daily-pm.md`](routines/daily-pm.md) — 日次PM巡回
- [`routines/weekly-growth.md`](routines/weekly-growth.md) — 週次CS/グロース便
- [`routines/weekly-summary.md`](routines/weekly-summary.md) — 週次経営サマリ＋自己点検

## ガードレール

**AIが自動で行ってよいこと**

- 社内DB（案件DB・タスクDB）の更新、完了確認済みタスクのクローズ
- 運行ボードへのログ・レポート・リマインド文面（コピペ用）の追記
- 提案書・週次報告・納品時3点セットの各種ドラフト生成
- 事業責任者宛の Gmail **下書き** 作成
- クライアント共有ページへの「確定済みの事実の進捗反映」のみ（変更内容は運行ログに必ず記録）

**Chatwork送信のルール（2026-08-28 藤原さん指示）**

- 社内スタッフへの連絡は「〇〇さん×マーケライン」形式のグループルームで行う
- 1対1の個別チャット（ダイレクトルーム）には基本送らない
- クライアント向け週次報告の文面は担当スタッフのグループルームへ配布し、現場から送ってもらう（事業責任者に送信実務を依頼するのは、炎上リスク案件・事業責任者窓口案件のみ）
- 全ての送信は文面提示→GO確認後に実行（既存ルール継続）

**機密情報の取り扱い(2026-09-01 藤原さん指示・厳守)**

- M&A・株式・個人資産・役員報酬に関する情報は、Notion(運行ボード・共有ページ含む)・Chatwork・Gmail等、スタッフや外部の目に触れうる場所に一切書かない。記録は藤原さんとのセッション内のみ
- 経営数字(利益・利益率・損益分岐・コスト内訳)も運行ボードには書かない。週次経営サマリの経営レポート部分はセッションチャット納品のみとし、ボードには案件進捗・機会損失(既知の契約月額ベース)だけを載せる

**AIが行わないこと（人間に残す）**

- クライアントへの送信（メール・LINE・チャットすべて。共有ページへの新たな対外約束の記載を含む）
- 金額・値引き・契約条件の提示や決定
- クライアント約束日（対外納期）の変更
- MTGの設定・出席

**既存業務ルールの継承**（オペレーションガイド準拠）

- 仕様凍結後の追加要望はパーキングロット行き（運用フェーズ or 追加見積）
- 即答禁止ゲート: 期日・可否は2営業日以内に3点セットで回答
- 納期未設定の進行中案件は黄色信号ON
- 値引きを標準化しない

## 実行基盤

- Routine（cron・UTC指定）が本セッション（コネクタ保持セッション）に発火する self-bind 方式
  - 日次PM: `0 23 * * 0-4`（= JST 平日 8:00）
  - 週次CS/グロース: `0 22 * * 0`（= JST 月曜 7:00）
  - 週次経営サマリ: `0 8 * * 5`（= JST 金曜 17:00）
- 新規セッション発火方式はコネクタ（Notion等）が引き継がれないため不採用（2026-07-26検証済み）

## 障害時の考え方

過去にPM自動化が約2週間停止しても誰も気づかなかった教訓から、
金曜の経営サマリにウォッチドッグ職務を内蔵する。日次・週次のログが運行ボードに
残っていない場合、週報の冒頭で「⚠️AI組織の運行異常」として必ず報告する。


## 送信文面の期限ルール(2026-09-03 藤原さん指摘で追加)

- **他のメンバーの作業期限を文面に書くときは、本人が合意した期限だけを書く。** AIが勝手に「黒崎から本日中に」等の第三者納期を約束しない。
- **夕方(17時)以降の依頼に「本日中」を書かない。** 標準は「翌営業日中」。急ぐ場合は本人に打診してから期限を書く。
- 対外(クライアント向け)文面に社内メンバーの納期を書く場合は、社内への依頼を先に出し、実現可能な期限で揃えてから対外文面に反映する(順序を逆にしない)。
- 背景: 9/3にスペクトラム統一ルームで「黒崎から本日中に」と18時台に2箇所書き、藤原さんが2度手動修正することになった。

## Chatwork送信前のルーム確認ルール(2026-09-05 藤原さん指摘・重大インシデントで追加)

- **社内向けメッセージ(コピペ用文面の配布・内部連絡等)を送る前に、必ずAPI(`/rooms/{room_id}/members`)で実際のメンバー一覧を取得し、クライアント側アカウントが含まれていないことを確認してから送信する。**
- **ルーム名やこれまでの印象で「社内ルームだろう」と判断しない。** 「★」プレフィックスや「〜プロジェクトチーム」等の名称は社内ルームとクライアント混在ルームの両方に使われており、名前だけでは判別できない。「〈社内〉」「【社内】」等の明示的な社内表記がある場合でも、初めて送信するルームは念のためメンバー確認を行う。
- 背景: 9/5、「★フジキプロジェクトチーム」ルーム(浜崎社長ほかフジキコーポレーション様側9名が参加する混在ルーム)を社内ルームと誤認し、内部向けの「先方へ送付をお願いします」という指示文言を含む週次報告ドラフトをそのままクライアントが見える形で送信してしまった。藤原さんが手動で削除・収拾した。
- このルールは既存の「Chatwork送信のルール(2026-08-28)」の実務上の前提条件であり、以後すべてのChatwork送信(内部・対外問わず)に適用する。
